# ADR-0001 — Shared simulator foundation with independent device modules

**Date:** 2026-10-13
**Status:** ACCEPTED FOR F0 PROTOTYPE ONLY; F1 fidelity approval HOLD

## Problem and outcome

Create a learning environment where students operate a convincing replica of the actual marine device, including key legends, control gestures, menus and alarm workflows. Begin with FCV-588, later add KODEN MDC-2060, AIS R5, FAR-2127, Navi-Sailor 4000, and the unresolved KODEN J2000 identity. A single scenario should eventually feed several different device types without putting instrument state or replay into the web UI.

## Constraints and non-goals

- Model/controller/firmware-specific UI and lesson truth. The FCV-588 prototype is deliberately provisional.
- Always training-only and isolated from real navigation and radio equipment. F0 must not send NMEA/AIS, open serial/RF hardware or access network data.
- No proprietary manufacturer artwork, logos, or manual pages embedded without permission.
- No source code copied from third-party GPL radar/simulator projects. Re-evaluate licensing if reuse is ever proposed.
- No full bridge 3D environment, microservices, production student accounts, multiplayer, or comprehensive AIS/RADAR/ECDIS before FCV-588 proof is sound.

## Options and decision

| Approach | Benefit | Principal risk | Decision |
| --- | --- | --- | --- |
| A. Separate application per hardware model | Quick one-off UI | Duplicate scenarios, teachers' workflow, replay and tests; difficult shared AIS/radar truth | Reject |
| B. Shared core + independent instrument-specific module | Shared simulation clock, fixture, teaching/scoring services; distinct physical panels and state machines | Requires small, strict type/event boundary; temptation to over-generalize | **Select** |
| C. Full bridge 3D/microservice simulator | Potentially extensible long-term | Expensive, licensing/compute/integration overhead not justified by first lesson | Defer |

The design assumes that a training scenario may be shared while display controls and behaviors must differ per model. If later real-equipment protocols become mandatory, re-evaluate the deployment boundary rather than opening ports in this F0.

## Runtime layers and contracts

~~~text
Teacher / Course shell          (no device-state ownership)
         |
Input adapter (mouse/key/touch -> normalized physical gesture)
         |
Device adapter FCV-588  [per-device pure reducer, semantic probes]
         |                              ^
Session runtime (canonical log, seq, simTick, replay)
         |                              |
World scenario -> sensor observation -> view projection -> canvas
         |
Future: radar, AIS R5, ECDIS module consume their own typed observations
~~~

### Key invariants

1. Session owns integer SimTick, world state, observation checkpoint, device state, held control edges and event log **separately**. A powered-off display cannot stop or change the world.
2. One reducer per physical device type. No cross-device menu state machine, all-in-one DeviceProfile DSL, or a universal sensor DTO.
3. Canonical InputEvent is a semantic hardware action (press, press edge, release edge, cancelled edge, knob rotate/push, trackpad direction). Browser DOM events never appear in the model.
4. Input/clock are processed deterministically; replay pins the core, scenario, profile, tick duration and named PRNG version, and rejects mismatches. Clock advancement happens explicitly, independent of rendering cadence.
5. Device Gain/Range can alter projected display, but not raw sensor observation or world position. Future typed effects require explicit sequencing and contracts, not a side-effectful reducer.
6. Sensor sample streams use stable stream names/counter mixes so adding an idle AIS module cannot alter sonar observations.
7. DeviceProfile JSON is static identity/evidence/compatibility metadata. Behavior stays in audited module code.
8. Browser pixels are not the grading source; future lesson scoring consumes semantic probes rather than DOM/CSS.

## Technology selected for F0

Native Node.js ES modules; node:test; browser HTML/CSS/Canvas 2D. This minimizes installation and provides fast deterministic contract testing on the existing Windows workstation. React/TypeScript is **not** installed in F0. A future conversion may be useful once UI navigation and the actual hardware identity are verified; keep source/boundary contracts portable.

## Threat and failure boundaries

The local demo binds only to 127.0.0.1, statically serves only web and src subtrees, sets restrictive CSP, and has no WebSerial/WebUSB/WebSocket/remote fetch path. Instructor-side grade/replay output is demonstrative and **not an anti-cheat trust boundary**. User-entered lesson text must eventually be escaped and rendered as text only. Simulation data is never navigation-authoritative.

## Approval gate

F0 technical demonstration: core replay/reset/world isolation tests GREEN, browser can boot/adjust display/reset/replay, no unauthorised network or equipment connection. F1 device-accurate phase: needs real machine imagery with permission, firmware and transducer identification, ten complete manual-backed student workflows, operator acceptance record, repeatable visual/behavior regression, and license approval. Until then, releaseApproval=HOLD.
